# 4.3.1 Struktur Arsitektur Modular Backend Service

Struktur backend service dibangun di atas tiga lapisan yang dipisahkan secara tegas, yakni lapisan *controller*, lapisan *service*, dan lapisan *schema*. Lapisan *controller* diberi tanggung jawab menerima *request* HTTP dan menyusun respons, lapisan *service* dipercayakan memuat aturan bisnis serta pelemparan eksepsi, dan lapisan *schema* ditetapkan sebagai representasi struktur dokumen pada basis data MongoDB. Pemisahan tersebut diperagakan melalui modul Autentikasi sebagai wakil.

Lapisan *controller* diwakili oleh berkas src/auth/auth.controller.ts. Setiap metode di dalamnya dibatasi hanya pada penerimaan *request* dan penerusan perintah kepada AuthService.

```typescript
@Controller('auth')
export class AuthController {
  constructor(private readonly authService: AuthService) {}

  @Post('register-company')
  @HttpCode(HttpStatus.OK)
  async registerCompany(@Body() registerCompanyDto: RegisterCompanyDto) {
    await this.authService.registerCompany(registerCompanyDto);
    return ResponseUtil.success('Verification code sent ...', null);
  }
  // ...
  @Post('login')
  @HttpCode(HttpStatus.OK)
  async login(@Body() loginAuthDto: LoginAuthDto) {
    const data = await this.authService.login(loginAuthDto);
    return ResponseUtil.success('Operation successful', data);
  }
}
```

<div align="center">Gambar 4.3 Potongan Kode Lapisan Controller</div>

Peran *controller* sebagai lapisan tipis diperlihatkan pada potongan tersebut. Objek masukan hanya diteruskan kepada AuthService dan hasilnya dibungkus melalui ResponseUtil.success, tanpa satu baris pun aturan bisnis dituliskan. Tanggung jawabnya terbatas pada pemetaan *route* dan penyeragaman format respons.

Lapisan *service* diwakili oleh berkas src/auth/auth.service.ts. Seluruh logika bisnis autentikasi dijalankan di dalamnya, sebagaimana ditunjukkan metode verifyOtp berikut.

```typescript
async verifyOtp(verifyOtpDto: VerifyOtpDto) {
  const email = verifyOtpDto.email.toLowerCase().trim();
  const pending = await this.pendingModel.findOne({ email }).exec();

  if (!pending) {
    throw new BadRequestException('No pending registration found ...');
  }

  if (pending.otpExpiresAt.getTime() < Date.now()) {
    await this.pendingModel.deleteOne({ _id: pending._id }).exec();
    throw new BadRequestException('OTP has expired ...');
  }
  // ...
  if (hashOtp(verifyOtpDto.otp) !== pending.otpHash) {
    pending.attempts += 1;
    await pending.save();
    throw new BadRequestException('Invalid OTP.');
  }
  // ...
}
```

<div align="center">Gambar 4.4 Potongan Kode Lapisan Service</div>

Konsentrasi aturan bisnis pada lapisan *service* dapat diamati melalui potongan tersebut. Masa berlaku *One Time Password* dievaluasi, kecocokan kode diverifikasi, dan setiap pelanggaran ditindaklanjuti dengan pelemparan BadRequestException. Tidak ada objek *request* HTTP yang disentuh pada metode ini.

Penegakan kontrol akses berbasis peran diwakili oleh berkas src/auth/guards/roles.guard.ts. Kelas RolesGuard memutuskan boleh atau tidaknya suatu *request* mencapai *handler* berdasarkan peran pengguna.

```typescript
canActivate(context: ExecutionContext): boolean {
  const requiredRoles = this.reflector.getAllAndOverride<string[]>(
    ROLES_KEY,
    [context.getHandler(), context.getClass()],
  );

  if (!requiredRoles) {
    return true;
  }

  const { user } = context.switchToHttp().getRequest();

  if (!user) {
    throw new ForbiddenException('User not found');
  }

  // Role Owner is always allowed (OP)
  if (user.role === 'owner_company') {
    return true;
  }

  if (!requiredRoles || !requiredRoles.some((role) => user.role === role)) {
    throw new ForbiddenException('You do not have permission ...');
  }
  return true;
}
```

<div align="center">Gambar 4.5 Potongan Kode Guard Penegakan RBAC</div>

Pembatasan peran per *endpoint* dijalankan melalui *guard* tersebut. Peran owner_company diberi hak penuh sehingga selalu diloloskan, sedangkan peran manager_company, staff, dan client hanya diloloskan apabila tercantum pada daftar peran yang disyaratkan *endpoint*. Pembagian hak akses keempat peran tersebut telah diuraikan pada Tabel 3.23 Daftar Peran beserta Hak Aksesnya.

Pemisahan lapisan inilah yang memungkinkan pengujian unit pada subbab 4.4.2 memverifikasi lapisan *service* tanpa dinyalakannya peladen maupun basis data. Ketiadaan ketergantungan lapisan *service* terhadap objek HTTP membuat logika bisnis dapat diuji melalui pemanggilan metode langsung dengan dependensi digantikan objek tiruan.

## CATATAN TEMUAN

Klaim inti didukung kode asli, namun beberapa hal perlu dirapikan agar narasi berlaku menyeluruh:

1. **Kopling HTTP di lapisan *service*.** Berkas src/auth/auth.service.ts masih memakai `HttpException` dan `HttpStatus` langsung pada `assertEmailAvailable` (baris 295–303), `resendOtp` (baris 111–118), `verifyOtp` (baris 265–268), dan `login` (baris 410–439). Potongan Gambar 4.4 memang bersih, tetapi metode lain belum. Saran: ganti dengan eksepsi semantik NestJS (`BadRequestException`, `ConflictException`).
2. **Peran sebagai *string* harfiah.** Pada roles.guard.ts baris 32, peran dibandingkan sebagai literal `'owner_company'`, bukan enum `Role`. Saran: gunakan `Role.CompanyOwner`.
3. **Logika kecil di *controller*.** Metode `logout` (auth.controller.ts baris 99–111) masih mengekstraksi dan memvalidasi header Authorization. Saran: pindahkan ekstraksi *token* ke *guard* atau *service*.

Poin 1 sebaiknya dirapikan lebih dulu, karena berkaitan langsung dengan pernyataan di bawah Gambar 4.4.
